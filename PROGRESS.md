- **Logic**: pre-handler, require the header (`IDEMPOTENCY_KEY_REQUIRED`, 400, seeded since P0-06 but never consumed until now), atomically claim the key (`INSERT`, primary key), or report `replay` (completed, same body+hash — short-circuits before the handler ever runs, returns the exact stored status+body), `body_mismatch` (same key reused with a different request body — 409, new `IDEMPOTENCY_KEY_CONFLICT`), or `in_progress` (same key, same body, still locked by a concurrent in-flight request — also 409, `details.reason` distinguishes the two). Post-handler: a success or a known `HttpException` (both deterministic, safe to replay) gets `complete()`d; anything else (a genuinely unexpected failure) gets `release()`d — deleting the row so a real retry can actually re-attempt the operation instead of being stuck replaying nothing. Both outcomes are awaited inline in the RxJS pipeline before the response is sent, not fired-and-forgotten, or an immediate client retry could race ahead of the write and see a false `in_progress`.
- **Real bug found and fixed during live verification, before it ever reached a test file**: the stored/replayed response body did not byte-match the original on the first attempt — not from `bigint`/`Date` serialization (the global `BigInt.prototype.toJSON` patch and `Date`'s native `toJSON` already normalize those identically whichever path serializes them), but because **Postgres `JSONB` does not preserve object key insertion order on round-trip**, unlike the plain `json` type. Fixed the comparison in the verify script to be structural, not string-based — and, as a defensive correctness fix in the shipped interceptor itself, both the completed and replayed values now go through one explicit `JSON.parse(JSON.stringify(...))` normalization pass before storage, so what's persisted is guaranteed to be exactly what Fastify's own serializer would have sent, not whatever shape Prisma's `Json`-column encoding happens to produce for a raw `bigint`/`Date`.
